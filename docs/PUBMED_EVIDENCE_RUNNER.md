The code intentionally contains **no TASK-0003 scientific queries**. The logical query-ID grammar remains `[A-Za-z0-9][A-Za-z0-9_.-]{0,127}` (excluding `.` and `..`); distinct valid suffix IDs including `A`, `A-00000`, and `A-00001` can coexist.

## Run-spec and deterministic identity

The versioned JSON spec includes `schema`, `task_id`, immutable `query_artifact` ref, logical `queries` map of **exact strings**, `operation: esearch-pmids`, `partition_policy: pubdate-bisect/v1`, inclusive date bounds, and explicit non-secret config refs (`NCBI_TOOL`, `NCBI_EMAIL`, optional `NCBI_API_KEY`). The executor also pins mode, Git commit SHA, runtime identity and attempt `1` (attempt is not mutable at retry; a correction requires a new versioned run-spec). Canonical JSON (UTF-8, sorted keys, compact separators) is SHA-256 hashed to derive `r-<32 hex>` run identity. A changed query/code/runtime creates a different ID; mutable wall-clock time is never an ID. Multiple attempts with the same identity cannot overwrite a final package; corrections need a new spec/attempt/version.

All requests use HTTPS ESearch POST, explicitly set `tool`/`email`, bound timeout (35 sec), bounded retry on 429/500/502/503/504/transient failures and ≤3 requests/s without an API key (≥0.36s spacing). Do not log HTTP request bodies or secret-bearing URLs. See [official NCBI E-utilities Help](https://www.ncbi.nlm.nih.gov/books/NBK25499/) and [NCBI usage guidance](https://eutilities.github.io/site/API_Key/usageandkey/).

PubMed **10,000-UID ceiling** is not bypassed using `retstart` or `usehistory`. Queries with source count ≥10,000 are recursively partitioned by *nonoverlapping inclusive publication dates*; each leaf must have count <10,000. Any single date retaining ≥10,000 fails closed. Raw count and ID responses are written before parsing. Reconciled PMID sets are positive decimal IDs, unique, numerically ascending, newline delimited; partition counts, duplicate counts and query-level unique union must agree with the source total. Publication-date omissions/out-of-range records cause a mismatch and **failure**, never silent loss. Root errors and warnings are preserved. This is a defensive, not scientifically validated, partition policy.

## Evidence layout and manifest

Approved path: `pubmed/{task_id}/{run_id}/` in **private** evidence repository; access class `project-internal`.

- `manifest.json`: schema/status, code/runtime, pinned query hashes/refs, timestamps, NCBI endpoint/method/tool/email, partition policy, file inventory (`SHA256`, bytes), reconciliation and root SHA-256.
- Canonical role-separated layout: query `queries/{qid}.txt`; raw ESearch `raw/{qid}/esearch/{sequence:05d}-{kind}.json` (`kind=count|ids`); raw EFetch attempt `raw/{qid}/efetch/{attempt:05d}.xml`; PMID union `pmids/{qid}/union.txt`; PMID leaf `pmids/{qid}/leaves/{leaf_index:05d}.txt`; selected sample `samples/{qid}/pmids.txt`. Each logical query ID is a separate validated path segment. `partitions/plan.json`: exact leaf queries and date boundaries; `reconciliation.json`: source count / unique count / duplicates / union hash; `metadata/requests.json`: endpoint, method, timestamp, query hash, response file. The optional `sample_policy` maps logical query IDs to an explicit `size` (1–100) and `sha256_prefix`; the PMID sample order is SHA256(prefix + PMID), and only NCBI EFetch PubMed XML is retrieved (no full texts). The raw XML is stored under `raw/`, its canonical PMID set under `samples/`; no scientific relevance classification occurs here.
- `samples/` is populated only when the separately authorized frozen spec declares `sample_policy`; EFetch stores PubMed XML (bibliographic metadata, titles, available abstracts), and validates PMID membership. A zero-result sampled query is a **valid final infrastructure state**: an empty `samples/{qid}/pmids.txt` is written, EFetch is **not called**, and **no sample XML** exists; this is not an empirical precision judgement. That judgement remains 01/TASK-0003’s responsibility. The SHA256 prefix must be copied verbatim from the frozen sampling protocol, not chosen by the runner.

Manifest root hash is `SHA256(canonical JSON of manifest with package_root_sha256 absent)`. `manifest.json` is excluded from file inventory to avoid recursion. Verify recomputes all file hashes, root hash, exact expected set of files derived from request/partition provenance (not merely declared inventory), source/leaf/union counts and numeric-sorted-unique PMID invariants. Strict allowlist of path IDs; symlink/path traversal and unexpected files rejected. Each final package ≤50 MiB, private repository must remain <1 GiB; no LFS, overwrite or force-push. Git evidence is **not** the canonical research raw/corpus store.

## Durable checkpoint state machine, correction and failure semantics (ADM-001)

The common **integrity gate** is `verify(package, require_final=False)`, also invoked by `git_write()` and before any resume network activity. Manifest schema `pubmed-evidence/v1` contains `query_states` for **every** frozen logical query and a failure marker on incomplete runs. States are `not_started`, transient `in_progress` (never serialized), `completed`, `failed_checkpointable` (resumable incomplete), and `failed_terminal` (terminal incomplete). In a persisted incomplete package, prior queries are `completed`, the failed query is `failed_checkpointable` or `failed_terminal`, and later queries are `not_started`. The exact `failure` object includes `query_id`, `stage`, `exception`, `disposition: resumable|terminal` and stable enumerated `reason_code`. All `queries/{qid}.txt` are materialized **before the first request**, including queries not yet started. No missing completed-query files are excused as not-started.

**Resumable incomplete** is durable only when the verifier independently replays a valid pending deterministic ESearch operation (`reason_code=search_pending`) or a retryable declared sample stage (`sample_retry`). Pre-response ESearch/EFetch outages, malformed/rejected COUNT or IDS responses and rejected EFetch XML remain retryable. Rejected raw attempts stay immutable; a resumed response uses a new attempt path. `prepare_resume` is allowed only after full `verify(require_final=False)`.

**Terminal incomplete** is durable *failure evidence*, never a successful/final query. State is `failed_terminal`, `disposition=terminal`, with exactly one independently rederived reason: `unsplittable_single_day_partition` (accepted COUNT ≥10,000 on a dated single-day span, no legal split, no IDS); `source_count_mismatch` (complete deterministic ESearch frontier and valid leaf raw/derived evidence, unique union size != root source count, no duplicates); or `cross_leaf_duplicate` (complete frontier, individually valid leaves, duplicate PMID(s) across leaves). For terminal reconciliation, no union/reconciliation entry is manufactured before mismatch. `verify(require_final=False)`, `git_write`, and explicit `readback --allow-incomplete` accept only independently proven terminal evidence; default final verify/readback reject. `prepare_resume` and local `collect --resume` reject **before any network activity**. A written terminal `run_id` is immutable: no checkpoint progression or overwrite. A changed strategy requires human/scientific decision and a new versioned run.

**Corruption/non-persistable failure** (tampered hashes, invalid plan identity, noncanonical source/derived lineage, divergent replay, unexplained completed-frontier errors or unsafe I/O) is neither valid terminal nor valid resumable evidence. A failed verifier means *no durable proof*. Received raw bytes are written before parse; pre-response outages have no fake raw file. The workflow must not claim a durable package until the private Git write **and independent fresh-runner exact-commit readback** both succeed. It then fails the workflow with a disposition-specific message for either incomplete outcome.

Every raw ESearch JSON response and raw EFetch XML response has an exact request metadata record with endpoint, method, timestamp, query/selection hash, file path and explicit outcome. Rejected parseable or malformed sample XML remains immutable at `raw/{qid}/efetch/00001.xml` (attempt 1) or `raw/{qid}/efetch/00002.xml`, `00003.xml`, etc. A retry creates the **next** immutable attempt; it never overwrites a previous failed attempt. Successful final sample selection comes only from the last **accepted** XML attempt, with exact frozen PMID identity. Previous failed XML attempts can coexist with this successful final response and retain their own provenance. The no-response EFetch outage has no XML attempt record until bytes actually arrive. ESearch requests are likewise append-only, with outcome/provenance and deterministic sequence numbers.

**Partial verifier:** exact manifest identity/schema, state consistency, safe file inventory/no symlinks, all file byte sizes/SHA256/root hash, all known query hashes, immutable response provenance, raw ESearch parse/outcome and raw-to-derived PMID/count reconciliation for every completed partition, all completed-query unions, and semantically declared rejected sample XML evidence. A not-started query may have *only its exact query file*. An interrupted query may legitimately lack unfinished PMID unions or an accepted sample; verified completed artifacts remain strict. Corrupt/missing content in any declared completed artifact is rejected. **Final verifier:** requires every query `completed`, complete partition/date coverage, exact counts/PMID unions, valid successful last XML attempt for each non-empty sample, zero-result empty sample without XML, and no pending failure state. Hashes alone never establish raw/derived consistency: verifier reparses ESearch count/idlist and matches accepted source evidence with stored derived counts/PMIDs; a rehashed but source-inconsistent package is rejected.

**Resume order:** (1) fetch/copy the private checkpoint; (2) verify complete stored hashes, root, provenance and declared partial-state semantics; (3) independently match spec/query/code/runtime identity; **only then** (4) issue new network calls. Replay already verified ESearch count/ids raw records without new network, including prior completed leaves; continue the exact deterministic frontier at the first missing or rejected operation. Rejected attempts are retained and retried as new immutable raw paths, never overwritten. Reuse already reconciled query PMIDs for a failed sample stage; skip completed sample retrieval; retry only unfinished/failed stages. An old failed sample response is never accepted or overwritten. For a resumable checkpoint only, a new ordinary Git commit contains updated derived checkpoint metadata and any new immutable responses; Git history is append-only and `--force` is forbidden. Neither earlier checkpoint commits nor a final package can be overwritten. Changed counts, mutated stored identity, corrupt completed artifacts or changed partition plan reject before unsafe reuse.

For an empty selected sample, the declared zero-result policy is **final + empty sample PMID file + no EFetch + no sample XML**. No inference about scientific precision follows from this infrastructure state. The runner never changes the frozen scientific sampling policy on its own.

Independent owner backup after **final** exact-commit readback remains required. Tests of temporary bare Git are offline implementation regression evidence only, *not* HOFF-0019 provisioning, real NCBI smoke, private-production write, independent readback, or owner-local backup acceptance. All such infrastructure acceptance gates remain separate and unverified until actual operational evidence arrives.

## P2-002 deterministic ESearch semantics (TASK-0011 replacement contract)

ESearch semantic role is derived by independent verifier-side deterministic execution-state reconstruction from the frozen exact query, pinned publication-date bisection policy, date bounds, and previously verified raw ESearch count results. It is **not derived from the filename suffix, persisted role label, retmax or response payload**. Those are checked *against* the expected operation. The root COUNT precedes any root IDS. When root COUNT < 10000, IDS follows with retmax equal to the verified count; **zero-result still requires COUNT then IDS**, both with retmax 0. A root count >=10000 starts the deterministic date frontier with no root IDS. Each partition COUNT precedes its IDS when count <10000; a partition COUNT >=10000 has no IDS and splits by the deterministic inclusive bisection rule. Counts within an unsplittable single-day partition fail closed.

The ESearch trace is validated in order and is prefix-closed: count, ids, query identity, canonical paths and per-query partition chronology must all match the replayed state. A rejected immutable count/ids response does not advance the semantic operation; a retry must use a new immutable request sequence/path for the same expected count or ids role. An incomplete checkpoint may stop only at the current operation (including a pre-response outage or rejected attempt), while completed queries require a full accepted trace. Resume calls the full strict checkpoint verifier **before network**, then reuses validated raw predecessor operations without recounting completed leaves and continues at exactly the pending frontier. The persisted partition plan corroborates the replayed trace; it never commands it.

The full-module P2-002 negative fixture creates a legitimate final zero-result package, swaps `00001-count.json` and `00002-ids.json` to opposite semantic suffixes without altering raw bytes or derived empty data, updates request references, metadata, file inventory hashes and package root, and demonstrates real `verify()` rejection on semantic role/order. Separate tests exercise nonzero count-to-ids, partition and nested splits, duplicate/missing/reordered operations, malformed and semantically rejected raw count/ids attempts, append-only retries, tampered failed checkpoints and hash-before-network resume. P2-001 canonical path namespace, ADM-001 durable EFetch checkpoints, raw-to-derived lineage and Stage 0 rev22 remain separate regression gates.

## D1 terminal-search failure disposition matrix (TASK-0013)

| Condition | Declared persisted state | Semantic invariant |
| --- | --- | --- |
| Pre-response ESearch network failure | resumable / `search_pending` | deterministic ESearch operation remains pending; no fabricated response |
| Malformed/rejected COUNT or IDS | resumable / `search_pending` | rejected raw immutable; pending semantic operation retried under new path |
| Interrupted deterministic frontier | resumable / `search_pending` | completed prefix verified; next operation exists |
| Pre-response EFetch failure or rejected XML | resumable / `sample_retry` | reconciled query present; accepted sample still missing |
| Single-day accepted COUNT ≥10,000 | terminal / `unsplittable_single_day_partition` | rederived dated single-day count; no IDS for that span |
| Complete frontier, union ≠ root count, no duplicates | terminal / `source_count_mismatch` | valid individual leaf raw/count/PMIDs and rederived distinct count |
| Complete frontier, duplicate PMIDs across leaves | terminal / `cross_leaf_duplicate` | individually valid leaves, independently rederived aggregate duplicate |
| Checkpoint identity/plan divergence, tamper, raw/derived corruption | **not persistable** | fail verification; cannot be labelled valid incomplete evidence |

The two-job workflow writes with repository-scoped **writer credential**, then does a fresh exact-commit readback using a distinct **read-only credential**. Readback compares status, root hash, disposition and reason code. Only afterward a terminal run prints “Durable terminal failure evidence verified; this run is not resumable.”; a resumable run prints “Durable resumable incomplete checkpoint verified; re-run with matching resume_id.”. Both then fail the workflow. Final readback remains strict by default and only a genuine final retrieval permits workflow success. This offline implementation contract is separate from operational HOFF-0019 acceptance and TASK-0003 scientific validation.
